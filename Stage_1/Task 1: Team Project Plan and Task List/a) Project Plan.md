## B. Project scope and learning goals

### Target learners and prerequisites
Target learners: Beginners taking Foundations of CS & AI who have little or no prior experience with hardware and behavioral AI. The explanations will assume basic reading and reasoning skills but will define module-specific terminology before using it. Any required mathematics, coding, or computing knowledge will be identified in the module outline and briefly reviewed where necessary.

### Proposed learning outcomes
By the end of the materials, a beginner should be able to:
- Define the key terms used in hardware and behavioral AI in their own words.
- Explain the main idea or process in a logical sequence and distinguish it from related concepts.
- Work through a representative example with intermediate steps shown.
- Apply the idea to a new beginner-level question or scenario and explain the answer.
- Identify at least one practical application and one limitation, common error, or misconception.

### Initial content outline and boundaries

| Section | Proposed coverage | Depth / boundary | Initial status |
| :--- | :--- | :--- | :--- |
| 1. Orientation and key terms | Why the module matters; essential vocabulary; prerequisites. | Brief introduction plus clear definitions. | Outline only |
| 2. Core concept A | Fundamental hardware components of AI systems, including CPUs, GPUs, memory, and storage; their functions and roles in supporting AI computation. | Detailed explanation with a simple illustration. | Outline only |
| 3. Core process or method | How AI hardware processes data and executes AI tasks, including data input, computational processing, memory access, and output generation; the interaction between hardware components and AI models. | Detailed step-by-step treatment; show intermediate steps. | Outline only |
| 4. Worked example | A representative example showing how an AI system uses hardware components to process input data and generate a behavioral response, explaining each stage of the process. | Fully worked and checked; explain why each step is taken. | Planned |
| 5. Application and limitations | Applications of hardware and behavioral AI in real-world intelligent systems, such as robotics and human-computer interaction; limitations related to computational resources, processing speed, power consumption, and the reliability of AI behavior. | Brief applications; explain one limitation or common misconception. | Planned |
| 6. Practice and review | Short questions, one application task, answer explanations, and test-bank questions. | Enough practice to check each learning outcome. | Planned |

### Scope boundaries and questions for the teacher
- Detailed treatment: the foundational concepts and one coherent process/example that beginners must understand to meet the learning outcomes.
- Brief treatment: advanced variations, specialist applications, historical background, and material not required by the course module unless the teacher confirms it is essential.
- Confirm with the teacher: Which subtopics are essential, expected technical depth, and whether any specific tools, algorithms, or frameworks are required.

### How the resources will support one another
1. Write and review the shared Markdown explanations, examples, activities, answers, and references first.
2. Adapt the reviewed content for each format: independent reading in the Study Guide, visual sequencing in slides, and narration or demonstration in videos.
3. Use the mini lecture to teach one focused idea from the same source, with an audience activity that checks understanding.
4. When content is corrected, identify every affected file, update those files, and recheck terminology, examples, and answers for consistency.

### GitHub, communication, and review practices
- Repository: [<https://github.com/rriscoj/TeamNameNotFound_GitHub_Markdown-V1>]. README will identify the team, module, members and usernames, project purpose, intended learners, folders, current progress, and remaining work.
- Suggested folders: /content, /assets, /examples, /study-guide, /slides, /videos, and /project-plan. Keep personal logs and private information out of a public repository.
- Commits: each member should make substantive contributions using their own account where practical. Commit messages should describe the actual change, for example “Add worked example for [concept]”. Do not create artificial commits.
- Communication: use wechat for quick coordination and hold a short review meeting in the library or dorm basement. Record decisions and action owners in meeting summaries.
- Review: each section should have an author and a peer reviewer. The author resolves comments, and the reviewer confirms the correction or records what remains unresolved.
- Correction propagation: maintain a simple change note listing the Markdown source changed and any Study Guide, slide, video, or test-bank item affected.
- Access: test repository permissions and confirm that the teacher can access the repository and linked materials. Required assessment content must also be included in submitted files.

### Risks and response plan

| Risk | Likely effect | Response |
| :--- | :--- | :--- |
| Module scope is unclear | Too much content or inconsistent depth. | Compare outline with course materials and ask the teacher focused questions early. |
| GitHub or Markdown unfamiliarity | Contributions or packaging are delayed. | Create a small test file early; share a short setup guide; save local backups and screenshots of meaningful work. |
| Incorrect or confusing explanation | Beginners cannot follow the material. | Use source checks, worked examples, peer review, and independent testing of all answers. |
| Uneven workload or delayed task | One member becomes a bottleneck. | Use small assignable tasks, visible status updates, early warnings, and reassignment by agreement. |
| Changes do not reach every resource | Study Guide, slides, videos, or answers contradict each other. | Record affected deliverables whenever Markdown changes and assign one person to verify consistency. |
| Missing logs or AI-use evidence | Contribution and process work becomes difficult to verify. | Record work and significant AI interactions when they occur; place evidence beside the relevant entry. |
| File or upload problems near deadline | Required work is missing or unreadable. | Package on Oct 23, extract ZIP into another folder, open every file, check links/assets, and submit early on Oct 24. |
